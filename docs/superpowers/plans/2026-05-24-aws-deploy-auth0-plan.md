# AWS Deploy & Auth0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Provision the AWS runtime (DynamoDB + Lambda + API Gateway HTTP API) and the Auth0 tenant via Terraform, then deploy the existing FastAPI backend (already shipped in Plan 1) so it serves authenticated requests at a real `https://...execute-api.us-east-2.amazonaws.com` URL.

**Architecture:** Two Terraform root modules under `infra/`: `platform/` (Auth0 only — long-lived identity) and `runtime/` (DynamoDB + Lambda + API Gateway — disposable compute). Both consume the S3 state bucket created by `infra/bootstrap/` (completed at the top of this plan, deferred from Plan 1). Backend code is packaged into a Lambda zip via uv and deployed via a small shell script that reads Terraform outputs.

**Tech Stack:** Terraform 1.6+ · AWS provider 5.x · Auth0 provider 1.x · AWS Lambda (Python 3.12, ARM64) · API Gateway HTTP API · DynamoDB on-demand · CloudWatch Logs (14-day) · Auth0 (Native iOS app, Apple Native Social, DB connection).

**Spec:** [`docs/superpowers/specs/2026-05-23-backend-infra-extraction-design.md`](../specs/2026-05-23-backend-infra-extraction-design.md)

**Plan 1 (predecessor):** [`docs/superpowers/plans/2026-05-23-backend-foundation-plan.md`](2026-05-23-backend-foundation-plan.md)

## Phase 0 — Manual external setup (NOT scripted)

These two pieces have to be done in a browser. Each leaves you with a set of values to record. **Save them in a password manager (1Password / Bitwarden), not in this repo.**

### Phase 0A — Auth0 tenant setup

**Goal:** Create an Auth0 tenant, register an API (which becomes the JWT audience), and create an M2M (machine-to-machine) application whose credentials the Terraform Auth0 provider uses.

1. **Sign up at https://auth0.com.** Free tier; no credit card required. Pick the region closest to us-east-2 (US — the default).
2. **Tenant name:** when prompted, choose a tenant subdomain. Suggested: `dualweather`. Your full domain becomes `dualweather.us.auth0.com` (or `.eu.` / `.au.` depending on region).
3. **Create the API:**
   - Dashboard → Applications → APIs → **+ Create API**.
   - **Name:** `Dual Weather API`
   - **Identifier:** `https://api.dualweather/` *(this exact string — it's the JWT `audience` claim; trailing slash matters)*
   - **Signing Algorithm:** `RS256`
   - Save.
4. **Create an M2M application for Terraform:**
   - Dashboard → Applications → Applications → **+ Create Application**.
   - **Name:** `Dual Weather Terraform`
   - **Type:** `Machine to Machine Applications`
   - **API to authorize:** select `Auth0 Management API`.
   - **Permissions (scopes) to grant** *(check each box; copy this list exactly)*:
     - `read:clients` `create:clients` `update:clients` `delete:clients`
     - `read:connections` `create:connections` `update:connections` `delete:connections`
     - `read:resource_servers` `create:resource_servers` `update:resource_servers` `delete:resource_servers`
     - `read:client_grants` `create:client_grants` `update:client_grants` `delete:client_grants`
   - Save.
5. **Record these values** (each will become a Terraform variable):
   - `AUTH0_DOMAIN` — e.g., `dualweather.us.auth0.com`
   - `AUTH0_CLIENT_ID` — from the M2M app's Settings → Basic Information
   - `AUTH0_CLIENT_SECRET` — from the M2M app's Settings → Basic Information (Show)

**Verification before continuing:** Run this curl command (substitute your values) to confirm the M2M credentials work:

```bash
curl -sf -X POST "https://${AUTH0_DOMAIN}/oauth/token" \
  -H 'Content-Type: application/json' \
  -d "{\"client_id\":\"${AUTH0_CLIENT_ID}\",\"client_secret\":\"${AUTH0_CLIENT_SECRET}\",\"audience\":\"https://${AUTH0_DOMAIN}/api/v2/\",\"grant_type\":\"client_credentials\"}" \
  | jq -r .access_token | head -c 30; echo
```

Expected: prints a long JWT prefix (an `eyJ...` string). If it errors, fix Auth0 setup before continuing.

### Phase 0B — Apple Developer setup (Sign in with Apple)

**Goal:** Provision the Apple-side credentials Auth0 needs to broker Sign in with Apple natively. This produces a `.p8` key + three short identifiers.

You need a paid Apple Developer Program membership ($99/year). If you don't already have one, **stop here** — the rest of Plan 2 can still proceed without Apple (only email/password sign-in will work) but the iOS plan (Plan 3) will need to skip the Apple path too.

1. **App ID:**
   - https://developer.apple.com/account → Identifiers → **+** → "App IDs" → "App".
   - **Description:** `Dual Weather iOS`
   - **Bundle ID:** must match your Xcode project's bundle ID. Check `frontend/Dual Weather iOS.xcodeproj` Build Settings → "Product Bundle Identifier", or open Xcode → target → Signing & Capabilities tab. Likely something like `com.b1codes.dualweather` or similar.
   - **Capabilities:** scroll down, check **Sign In with Apple**.
   - Continue → Register.
2. **Services ID** *(distinct from App ID — this is what Auth0 will use)*:
   - Identifiers → **+** → "Services IDs".
   - **Description:** `Dual Weather Auth0`
   - **Identifier:** by convention, append `.auth` to your bundle ID, e.g., `com.b1codes.dualweather.auth`. Record this — it becomes the `APPLE_SERVICES_ID` Terraform variable.
   - Continue → Register.
   - After registration, click the new Services ID → enable **Sign In with Apple** → click **Configure**:
     - **Primary App ID:** select the App ID from step 1.
     - **Domains and Subdomains:** `dualweather.us.auth0.com` (your Auth0 domain — no protocol, no path).
     - **Return URLs:** `https://dualweather.us.auth0.com/login/callback` (full URL).
     - Save → Continue → Save.
3. **Sign in with Apple key:**
   - Keys → **+** → register a new key.
   - **Key Name:** `Dual Weather Sign in with Apple`
   - Check **Sign In with Apple** → **Configure** → choose your App ID from step 1 → Save.
   - Continue → Register.
   - **Download the `.p8` file** — you can only download once. Save it somewhere safe (e.g., `~/keys/dualweather-siwa.p8`). Note the **Key ID** shown on the page (10 chars).
4. **Team ID:** top-right of any Apple Developer page, next to your name, in parentheses. 10 chars.
5. **Record these values:**
   - `APPLE_TEAM_ID` — e.g., `V52XCTXQTY`
   - `APPLE_SERVICES_ID` — e.g., `com.b1codes.dualweather.auth`
   - `APPLE_KEY_ID` — e.g., `ABC123DEF4`
   - `APPLE_KEY_FILE_PATH` — absolute path to your downloaded `.p8`, e.g., `/Users/yourname/keys/dualweather-siwa.p8`

**Phase 0 complete checklist:**

- [ ] `AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET` recorded
- [ ] Auth0 API created with identifier `https://api.dualweather/`
- [ ] M2M token validation curl returns a JWT
- [ ] Apple App ID created with Sign in with Apple capability
- [ ] Apple Services ID created and configured with Auth0 callback URL
- [ ] `.p8` key downloaded and saved (NOT in this repo)
- [ ] `APPLE_TEAM_ID`, `APPLE_SERVICES_ID`, `APPLE_KEY_ID`, `APPLE_KEY_FILE_PATH` recorded

Now create a local shell init file (NOT in the repo) so subsequent terraform commands can read these via env vars:

```bash
# ~/.dual-weather-secrets.sh (chmod 600)
export AUTH0_DOMAIN='dualweather.us.auth0.com'
export AUTH0_CLIENT_ID='...'
export AUTH0_CLIENT_SECRET='...'
export TF_VAR_auth0_domain="$AUTH0_DOMAIN"
export TF_VAR_auth0_client_id="$AUTH0_CLIENT_ID"
export TF_VAR_auth0_client_secret="$AUTH0_CLIENT_SECRET"
export TF_VAR_apple_team_id='V52XCTXQTY'
export TF_VAR_apple_services_id='com.b1codes.dualweather.auth'
export TF_VAR_apple_key_id='ABC123DEF4'
# .p8 content as a single string (line breaks preserved)
export TF_VAR_apple_signing_key="$(cat ~/keys/dualweather-siwa.p8)"
# iOS bundle ID — must match Xcode project's Product Bundle Identifier.
export TF_VAR_ios_bundle_id='com.b1codes.dualweather'
```

Source this before each `terraform` command: `source ~/.dual-weather-secrets.sh`.

```hcl
# The API definition — its identifier becomes the JWT audience.
resource "auth0_resource_server" "api" {
  name        = "Dual Weather API"
  identifier  = var.auth0_audience
  signing_alg = "RS256"

  # Tokens are valid for 24h; access tokens get refreshed by Auth0.swift's CredentialsManager.
  token_lifetime         = 86400
  skip_consent_for_verifiable_first_party_clients = true
}

# Native iOS application client (the iOS app's Auth0 client).
resource "auth0_client" "ios_app" {
  name        = "Dual Weather iOS"
  description = "Native iOS app for Dual Weather"
  app_type    = "native"

  is_first_party             = true
  oidc_conformant            = true
  cross_origin_authentication = false

  grant_types = [
    "authorization_code",
    "refresh_token",
  ]

  callbacks = [
    "${var.ios_bundle_id}://${var.auth0_domain}/ios/${var.ios_bundle_id}/callback",
  ]

  allowed_logout_urls = [
    "${var.ios_bundle_id}://${var.auth0_domain}/ios/${var.ios_bundle_id}/callback",
  ]

  refresh_token {
    rotation_type   = "rotating"
    expiration_type = "expiring"
    leeway          = 0
    token_lifetime  = 2592000  # 30 days
  }

  jwt_configuration {
    alg = "RS256"
  }
}

# Apple Sign-In as a Native Social connection.
resource "auth0_connection" "apple" {
  name     = "apple"
  strategy = "apple"

  options {
    client_id     = var.apple_services_id
    team_id       = var.apple_team_id
    key_id        = var.apple_key_id
    client_secret = var.apple_signing_key

    scope = "name email"

    # Allow the connection to operate on the iOS native social flow only.
    set_user_root_attributes = "on_each_login"
  }
}

# Username/password database connection (the email-sign-in fallback).
resource "auth0_connection" "database" {
  name     = "Username-Password-Authentication"
  strategy = "auth0"

  options {
    password_policy = "good"

    password_complexity_options {
      min_length = 8
    }

    # Lenient brute-force protection for v1 — Auth0's default is reasonable.
    brute_force_protection = true

    # Sign-up enabled by default for v1; can be tightened later.
    disable_signup = false

    enabled_database_customization = false
  }
}

# Bind both connections to the iOS client.
resource "auth0_connection_clients" "apple_to_ios" {
  connection_id = auth0_connection.apple.id
  enabled_clients = [
    auth0_client.ios_app.id,
  ]
}

resource "auth0_connection_clients" "database_to_ios" {
  connection_id = auth0_connection.database.id
  enabled_clients = [
    auth0_client.ios_app.id,
  ]
}

# Grant the iOS client access to the API (audience).
resource "auth0_client_grant" "ios_to_api" {
  client_id = auth0_client.ios_app.id
  audience  = auth0_resource_server.api.identifier

  scopes = []  # No scoped permissions in v1 — every authenticated request gets full access.
}
```

## Task 11: Backend Lambda build script

**Files:**
- Create: `backend/scripts/build_lambda.sh`

- [ ] **Step 1: Create `backend/scripts/build_lambda.sh`**

```bash
#!/usr/bin/env bash
# Build a Lambda deployment zip from the dual_weather backend.
#
# Output: backend/build/lambda.zip
#
# Strategy:
#   1. uv exports the pinned dependencies as requirements.txt (locked).
#   2. uv pip install --target build/staging installs them flat (Lambda's expected layout).
#   3. Copy src/dual_weather/ into build/staging/.
#   4. Zip the contents of build/staging/ into build/lambda.zip.

set -euo pipefail

BACKEND_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
STAGING="${BACKEND_DIR}/build/staging"
ZIP_OUT="${BACKEND_DIR}/build/lambda.zip"

rm -rf "${BACKEND_DIR}/build"
mkdir -p "${STAGING}"

echo "[build_lambda] Exporting pinned requirements"
cd "${BACKEND_DIR}"
uv export \
  --frozen \
  --no-dev \
  --no-emit-project \
  --format requirements-txt \
  > "${BACKEND_DIR}/build/requirements.txt"

echo "[build_lambda] Installing deps into staging/"
uv pip install \
  --target "${STAGING}" \
  --requirement "${BACKEND_DIR}/build/requirements.txt" \
  --python-platform aarch64-manylinux2014 \
  --python-version 3.12 \
  --only-binary=:all:

echo "[build_lambda] Copying source"
cp -R "${BACKEND_DIR}/src/dual_weather" "${STAGING}/dual_weather"

# Strip cache + bytecode that bloat the zip without serving Lambda.
find "${STAGING}" -type d -name '__pycache__' -prune -exec rm -rf {} +
find "${STAGING}" -type f -name '*.dist-info' -prune -exec rm -rf {} + 2>/dev/null || true

echo "[build_lambda] Zipping"
cd "${STAGING}"
zip -qr "${ZIP_OUT}" .

SIZE_KB=$(du -k "${ZIP_OUT}" | cut -f1)
echo "[build_lambda] Done — ${ZIP_OUT} (${SIZE_KB} KB)"
```

## Task 12: Backend deploy script

**Files:**
- Create: `backend/scripts/deploy.sh`

- [ ] **Step 1: Create `backend/scripts/deploy.sh`**

```bash
#!/usr/bin/env bash
# Upload backend/build/lambda.zip to the deployed Lambda.
#
# Reads function name from Terraform output. Does NOT modify Terraform state.

set -euo pipefail

BACKEND_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
INFRA_RUNTIME="${BACKEND_DIR}/../infra/runtime"
ZIP_PATH="${BACKEND_DIR}/build/lambda.zip"

if [ ! -f "${ZIP_PATH}" ]; then
  echo "[deploy] ${ZIP_PATH} not found. Run 'make package' first." >&2
  exit 1
fi

echo "[deploy] Reading function name from ${INFRA_RUNTIME}"
FUNCTION_NAME=$(terraform -chdir="${INFRA_RUNTIME}" output -raw function_name)
REGION=$(terraform -chdir="${INFRA_RUNTIME}" output -raw 2>/dev/null api_url | sed -E 's#https://[^.]+\.execute-api\.([^.]+)\..*#\1#')
REGION="${REGION:-us-east-2}"

echo "[deploy] Uploading ${ZIP_PATH} to function ${FUNCTION_NAME} in ${REGION}"
aws lambda update-function-code \
  --region "${REGION}" \
  --function-name "${FUNCTION_NAME}" \
  --zip-file "fileb://${ZIP_PATH}" \
  --publish \
  --output text \
  --query 'FunctionArn'

echo "[deploy] Waiting for code update to finish"
aws lambda wait function-updated --region "${REGION}" --function-name "${FUNCTION_NAME}"

# Switch the handler from the placeholder's "handler.handler" to the real backend's entry point.
# Idempotent: if it's already set, this is a no-op and AWS returns ResourceConflictException
# only when an update is in flight (handled by the prior `wait`).
echo "[deploy] Ensuring handler is set to dual_weather.main.handler"
aws lambda update-function-configuration \
  --region "${REGION}" \
  --function-name "${FUNCTION_NAME}" \
  --handler dual_weather.main.handler \
  --output text \
  --query 'LastUpdateStatus' > /dev/null

aws lambda wait function-updated --region "${REGION}" --function-name "${FUNCTION_NAME}"

echo "[deploy] Done"
```

## Task 15: End-to-end authenticated smoke test

- [ ] **Step 1: Get a real Auth0 access token**

In your browser:
- Auth0 dashboard → Applications → APIs → `Dual Weather API` → **Test** tab.
- Copy the curl command's `access_token` value (the long JWT after `Authorization: Bearer `).
- Alternatively, in a terminal:

```bash
source ~/.dual-weather-secrets.sh
curl -sf -X POST "https://${AUTH0_DOMAIN}/oauth/token" \
  -H 'Content-Type: application/json' \
  -d "{\"client_id\":\"${AUTH0_CLIENT_ID}\",\"client_secret\":\"${AUTH0_CLIENT_SECRET}\",\"audience\":\"https://api.dualweather/\",\"grant_type\":\"client_credentials\"}" \
  | jq -r .access_token
```

That curl uses the Management API M2M creds to get a token for the API audience. It works because `auth0_client_grant.ios_to_api` allows the iOS client → audience, but for testing purposes, the M2M-via-management-API approach also yields a valid token.

> **Note:** the M2M-issued token has a `sub` claim like `<client_id>@clients` rather than `apple|...` or `auth0|...`. The backend will still accept it (`current_user` reads any `sub`), and `get_or_create_profile` will create a row keyed on that sub. This is fine for the smoke test — clean up the row later if you care.

- [ ] **Step 2: Run the smoke-prod target**

```bash
export AUTH0_TOKEN='eyJhbG...'  # paste from Step 1
cd backend && make smoke-prod
```

Expected three blocks of output:
1. `{"status":"ok"}` from `/health`.
2. A new location object with a server-generated `id` and `created_at` from `POST /locations`.
3. A list containing that single location from `GET /locations`.

If `make smoke-prod` fails on the POST step with 401, your token's audience may not match `https://api.dualweather/` exactly. Double-check by decoding the JWT (paste at https://jwt.io) and confirming the `aud` claim.

- [ ] **Step 3: Confirm Dynamo has the row**

```bash
aws dynamodb scan \
  --region us-east-2 \
  --table-name DualWeather \
  --query 'Items[*].{pk:pk.S,sk:sk.S,city:city.S}'
```

Expected: at least one item with `pk = USER#<client_id>@clients` and an `sk` starting with `LOC#`, city `"Austin"`, plus the lazily-created `PROFILE` row.

- [ ] **Step 4: Tail Lambda logs for the smoke run**

```bash
aws logs tail "/aws/lambda/dual-weather-api" --region us-east-2 --since 5m --follow
```

You should see FastAPI access logs for each call. Cancel with Ctrl-C.
